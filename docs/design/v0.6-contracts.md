# v0.6 contracts: hardening and deliverability

v0.6 fixes every proven finding from the v0.5.0 audit and adds the features that put OpenMailWire ahead on security, inbox placement and agent safety. Work is split into lanes by area, so each file has one owner.

## Shared rules

The rules in [roadmap-contracts.md](roadmap-contracts.md) still apply: Go 1.25 locally (`GOTOOLCHAIN=local`, `GOPROXY='https://proxy.golang.org|direct'`), gofmt/vet/race-clean, end-to-end tests built on `newEnv` in new files, no `t.Parallel` in `internal/e2e`, no real mail, no logging of bodies or full addresses, README and CHANGELOG updated under `## Unreleased`.

Additions:
- **Regression tests:** every fixed finding gets a test that failed before the fix. Reuse the auditors' proof tests:
  - `~/Documents/openmailwire-wt/audit-r1-api/internal/{e2e,api}/audit_r1_test.go`;
  - `~/Documents/openmailwire-wt/audit-r3-delivery/internal/{e2e,worker,message}/audit_r3_test.go`;
  - `~/Documents/openmailwire-wt/audit-r4-surfaces/internal/{e2e,webhook,mailparse}/audit_r4_test.go`;
  - R2's tests, when its report is in.
- **Disk:** the disk is nearly full (about 11 GB free). Don't keep fuzz corpora, coverage files or binaries. Delete what you create.
- **Errors for agents:** new refusals use the existing error shape, and the message names the cause and the next step.

## Lane A: API correctness and hardening

**Audit fixes:**
- R1#3: a second `From :` header (space before the colon) slips past the raw path's checks. Count From/To/Cc/Bcc on trimmed header names, require exactly one From, and refuse header names with whitespace before the colon.
- R1#4: domain names are unique across projects. Make them unique only among verified domains; expire unverified claims after 7 days, and let a project verify a name another project only claimed.
- R1#5: memory per large request. Add a server-wide semaphore for bodies over 1 MB, cut the copies, and add per-key request rate limits (a token bucket; `429 rate_limit_exceeded` with `Retry-After`).
- R1#6: scope idempotency keys to the API key.
- R1#7: give batch items their own idempotency namespace.
- R1#8: text Postgres can't store (NUL, invalid UTF-8) must answer 422, never 500, on every path.
- R1#9 and R3#10: fold header lines and never write a line over 998 bytes. Cap display names, `content_type` and subject.
- R1#10: truncate reply subjects on every path.
- R4#5: HTTP server timeouts (`ReadTimeout`, `WriteTimeout` large enough for 20 MB bodies, `IdleTimeout`, `MaxHeaderBytes`), and default `OMW_LISTEN` to `127.0.0.1:8080`.
- R4 (informational): `nosniff` and `Cache-Control: no-store` on API responses. `/health` stops reporting the version unless authenticated.

**Features:**
- A `text/plain` part is generated from HTML when only `html` is given.
- API keys gain `allowed_ips` (CIDR list) and `expires_at`.
- An append-only audit log: who did what (key, domain, webhook, inbox and approval changes) with the acting key, readable at `GET /audit-log` (full access). Each row carries the SHA-256 of the previous row, so tampering shows.
- Domains:
  - DMARC (at least `p=none`) becomes a required record;
  - the return-path MX is shown by default, and becomes required whenever `OMW_BOUNCE_MX` or an inbound host is configured;
  - verification explains the Gmail, Yahoo and Microsoft rules in the record details.

## Lane B: agent safety and compliance

All server-enforced, all usable from MCP. Changes to `authorizeSend` live here.

**Approval holds:**
- Key policy `require_approval`, with rules: `always`, `first_contact` (recipient never mailed by this project), `has_attachments`, `has_links`, `recipients_over: N`.
- A matching send is stored with delivery status `held` (extend the CHECK) and fires event and webhook `email.held`.
- `POST /emails/{id}/approve` and `POST /emails/{id}/reject` need full access or a key with `can_approve`. The approver is recorded in the audit log, and the events are `approved` / `rejected`.
- Held mail expires with `expires_at`.
- MCP: `send_email` reports "held for approval"; new tools `list_held` and `approve_email` / `reject_email`. Those two are only for keys allowed to approve, and are marked destructive.

**Suppressions API:**
- `GET /suppressions` (filters, pagination), `POST /suppressions` (add with a reason), `DELETE /suppressions/{address}`, `GET /suppressions/export` (CSV).
- Full access to change; sending keys may read.

**Streams and one-click unsubscribe:**
- `stream: "transactional" | "broadcast"` on sends (default `transactional`).
- `broadcast` mail automatically gets `List-Unsubscribe: <https://…/u/{token}>, <mailto:…>` and `List-Unsubscribe-Post: List-Unsubscribe=One-Click` (RFC 8058). The token is HMAC-signed over the project and address.
- `POST /u/{token}` (no auth) suppresses at once (reason `unsubscribe`, stream scope `broadcast`). `GET` shows a minimal confirm page that never unsubscribes on GET, because link scanners follow links.
- Broadcast mail without a resolvable public base URL (`OMW_PUBLIC_URL`) is refused with a clear error.

**`Feedback-ID`:** added automatically as `<stream>:<api key id>:<project id>:omw`. Gmail's feedback loop reports by this header.

**Frequency cap per recipient, across all agents:**
- Project setting `max_per_recipient_per_day` (default off), enforced in `authorizeSend`.
- Refusal: `429 recipient_rate_limited`.

**Circuit breakers:**
- Rolling bounce and complaint rates per API key, per sending domain and per project.
- Defaults: pause when bounces > 5% or complaints > 0.1%, over at least 50 recipients in 24 h.
- A paused scope refuses sends with `403 sending_paused`, naming the rate, the scope and how to resume. It fires webhook `sending.paused`.
- `POST /pauses/{id}/resume` needs full access and is logged.

**Pre-send check:** `POST /emails/check` takes the same body as `POST /emails`, sends nothing, and returns warnings:
- no text part;
- HTML over 102 KB (Gmail clips it);
- link domains not matching the From domain;
- a missing unsubscribe on broadcast;
- the domain not verified;
- policy refusals that would apply;
- size.

MCP tool `check_email`.

## Lane C: delivery and deliverability

**Audit fixes:**
- R3#1: the throttle classification. Only connection or IP-level signals count. Authentication-related codes (4.7.26–4.7.32) are recorded per sending domain and project instead. A shared limit is halved only when deferrals come from at least 2 distinct recipients.
- R1#2 and R3#2: cancel or expiry racing a lease. Re-check status in the locked step.
- R3#3: scheduled mail gets its Date header and DKIM signature when it is leased (re-sign at lease time).
- R3#4: truncate on UTF-8 rune boundaries everywhere.
- R3#5: DATA timeouts as in RFC 5321: a deadline per block, then about 10 minutes for the final reply.
- R3#6: a job must finish before its lease expires, with a margin.
- R3#7: release a lease the worker cannot unseal.
- R3#8: lock ordering between ReportAttempt and Sweep.
- R3#9: keep a 4xx/5xx reply to EHLO.
- R3#11: opportunistic TLS may use TLS 1.0+. MTA-STS and DANE keep 1.2+.
- R3#12: 8BITMIME/SMTPUTF8 negotiation. Defer with 5.6.3 when the server can't take the message.
- R3#13: lease performance.
- R3 unproven:
  - DANE with only unusable TLSA records still requires TLS;
  - the MX lookup goes through the validating resolver when DANE is on;
  - MTA-STS policies refresh before they expire;
  - unknown report fields are tolerated, for version skew.

**Features:**
- **Throttling per mailbox provider:** recipient domains group by MX provider (google, microsoft, yahoo, apple, zoho and others, detected from MX host suffixes and cached). Limits and backoff apply per provider and sending IP, and a rules file is shipped.
- **Automatic IP warm-up:** each sending IP ramps up per provider on a configurable daily schedule (built-in default curve). Overflow waits or goes to a relay worker when one is live. Remaining capacity shows in `openmailwire workers list`.
- **Worker self-check at start:** `OMW_EHLO` is an FQDN; its A record matches `OMW_PUBLIC_IP`; the PTR of `OMW_PUBLIC_IP` matches `OMW_EHLO` (forward-confirmed reverse DNS); port 25 egress works. It refuses to start on failure unless `OMW_SKIP_SELF_CHECK=true` (development). Results are reported in the heartbeat.
- **Retries:** the first retry comes after 5–15 minutes. Greylisting replies are recognised and don't count toward the relay hand-over.
- **DKIM:**
  - oversign From, To, Subject, Date, Message-ID, Reply-To and Cc;
  - optional Ed25519 signing next to RSA (domain setting, which adds a DNS record);
  - key rotation with two selectors and an overlap: `POST /domains/{id}/dkim/rotate` in a NEW file, `internal/api/dkim.go`.
- **Connection reuse:** one connection per MX carries several messages, with RSET in between, within the concurrency limits.
- **Worker token roles:** tokens get kind `delivery`, `inbound` or `relay`. Inbound endpoints refuse delivery tokens, and the reverse.

## Lane D: inbound trust (brief follows R2's report)

**Audit fixes:** R2's findings, R1's note that complaint lookup by Message-ID is global, and R4#9: seal the inbound snippet.

**Features:**
- **A trust verdict on received mail:** SPF, DKIM and DMARC evaluated, stored as `authentication_results`. `trust: "authenticated" | "unauthenticated" | "failed"` is returned by the API, webhooks and MCP tools. Inbox setting `hold_unauthenticated` defaults to on for agents.
- **Prompt-injection framing:** MCP output marks every piece of sender-controlled text as untrusted. An optional rules hook flags common injection patterns.
- **ARF:** reports must come from DKIM-verified feedback-loop domains, or through VERP.
- **Limits:** per-IP rate limits and an RCPT check cache. `postmaster@` and `abuse@` work.
- **DMARC aggregate reports** (RFC 7489 and the 2026 DMARCbis, `rua=`) and **TLS-RPT** (RFC 8460) are received through inbound, parsed and stored. `GET /domains/{id}/reports` shows authentication pass rates by source and lists unknown senders.

## Lane E: platform, webhooks and supply chain

**Audit fixes:**
- R1#1 and R4#1: webhook fan-out. Drop the id cursor: track fan-out per event (e.g. a `fanned_out` column plus `FOR UPDATE SKIP LOCKED`, or an outbox written in the same transaction), with no changes needed at event insert sites.
- R4#4: fairness. Webhooks per project are capped (default 10), claims are spread across projects and endpoints, a circuit breaker covers each endpoint, and nothing waits on a whole batch.
- R4#6: connection limits (`IdleConnTimeout`, `MaxIdleConns`).
- R4#7: SSRF covers NAT64 and 6to4. Only global unicast is allowed, minus the IANA special-purpose ranges.
- R4#8: generic `last_error` for tenants; details go to the log.
- R4#2 and R4#3:
  - CI and release build with Go 1.27.x (`check-latest`);
  - govulncheck runs in CI;
  - the Docker builder is current Go and the runtime is current Alpine, pinned by digest;
  - `go.mod` gets a `toolchain` line.
- R4#10: the Python SDK never sends the key on redirects. Check the other SDKs too.
- R4#11:
  - actions pinned by SHA;
  - least-privilege `permissions` in every workflow;
  - releases build outside the source tree;
  - build provenance attestations;
  - checksums signed.
- R4 informational: verify `OMW_SECRET_KEY` at startup against a stored check value.

**Features:**
- **Secret rotation:**
  - sealed values carry a key id;
  - `OMW_SECRET_KEYS` holds several keys, the first used for new seals;
  - `openmailwire rotate-secrets` re-seals in the background.
- **Webhook secret rotation:** `POST /webhooks/{id}/rotate-secret` with an overlap window during which both signatures are sent.
- **Asymmetric webhook signatures:** optional Ed25519 (`v1a`, Standard Webhooks), with the public key published at `GET /webhooks/{id}`.
- **Delivery insights:** `GET /insights` (full access) returns acceptance, deferral and bounce rates and p50/p95 time to acceptance, per mailbox provider and per sending IP, for 24 h, 7 d and 30 d. It is computed from attempts with indexed, bounded queries.
